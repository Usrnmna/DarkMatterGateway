# Programming index

This index maps the available Matter IR Terminal source to its responsibilities, build inputs, interfaces, and verification evidence. It covers the ESP32-S3 firmware, portable IR library, appliance configuration, host utilities, tests, CI, and supporting engineering files. Detailed operating instructions remain in the linked guides.

The [prioritized remaining-work checklist](remaining-work.md) separates missing programming, appliance configuration, software verification, and physical hardware testing, with completion criteria and dependencies.

**Inventory date: 2026-10-28.** The workspace contains one maintained ESP-IDF application targeting `esp32s3`, with an optional Python serial client. No separate web, mobile, cloud application, or second firmware target was found in the maintained source. This is a description of the available implementation, not approval of an architecture or proof that every intended project requirement has been captured.

The initial inventory covered 54 existing maintained files, plus this index. Subsequent additions include the remaining-work checklist, [direct service/storage harness](../tests/service_stubs/README.md), [Matter/startup harness](../tests/app_stubs/README.md), test suites, mutation runners, and local exporter listed below. A separately catalogued Proflame 2 reference collection was also present at the initial inspection. Git metadata was absent initially; later concurrent Git state is recorded in [M1/M2 verification](validation.md#m1-and-m2-local-export-verification-2026-10-28) and does not establish a published firmware revision. Imported reference code, downloaded dependencies, and generated output are classified separately; private configuration, captures, credentials, and caches are excluded from the maintained-file inventory.

## Scope and evidence

Status terms distinguish different kinds of completeness:

- **Implemented:** executable source is present and its responsibility was inspected. This does not establish successful operation on hardware.
- **Configuration:** declarative input or integration definition exists; it is not an independent application.
- **Test stub:** a deliberate host-test replacement for SDK or device behavior, not production firmware.
- **Documented only:** a procedure or proposed interface is described without an implemented or verified path in the inspected source.
- **Partial / unclear:** the available material establishes a limitation or unresolved scope question, not an approved requirement to add a feature.

The [validation report](validation.md) records refreshed host checks and default/light-fan target builds for S1/S2 on **2026-10-28**, followed by direct service/storage coverage for S3/S4 and Matter/startup coverage for S5/S6 on the same date. [M1/M2 verification](validation.md#m1-and-m2-local-export-verification-2026-10-28) adds the scoped requirements record, local artifact exporter, fresh builds, and final package/host checks. Earlier software and documentation evidence remains dated in that report; each result retains its stated limits.

The report describes an unbuilt prototype with no flashing or physical qualification. The index therefore makes no claim of verified peripheral timing, flash retention, Matter commissioning, optical delivery, or appliance response. The [bring-up procedure](bring-up.md) remains the reference for those checks.

The core validates 30–60 kHz carrier frequencies, 10–50% replay duty, and frames no longer than 500 ms. Its 4,096-entry bound combined with an odd duration count permits at most 4,095 alternating durations. The [capture boundaries](operation.md#capture-boundaries) explain the separate hardware-buffer and single-frame limits. No appliance-specific protocol encoder or built-in command database is present in this library.

## Suggested reading and development order

This order follows existing dependencies. Development steps apply when their corresponding changes are authorized; the index itself makes no source, target, or architecture changes.

1. **Establish scope and evidence.** Read the [project overview](../README.md), [validation report](validation.md), and gaps above. Resolve any additional product requirements before expanding targets or hardware roles.
2. **Understand the hardware contract.** Read the [hardware design](hardware-design.md), [GPIO schedule](../hardware/gpio-map.csv), and [board constants](../firmware/main/board_config.hpp). Treat optional pins separately from implemented interfaces.
3. **Trace the portable data model.** Read [ir_core.hpp](../firmware/components/ir_core/include/ir_core.hpp), [ir_core.cpp](../firmware/components/ir_core/ir_core.cpp), and [core tests](../tests/test_ir_core.cpp) before modifying waveform, record, or fan-mapping behavior.
4. **Trace configuration into firmware.** Follow [devices.json](../config/devices.json) through the [validator/generator](../tools/profile_config.py), [profile tests](../tests/test_profiles.py), and [main CMake](../firmware/main/CMakeLists.txt). Separate aliases from actual learned waveforms.
5. **Follow device services and control paths.** Read the [IR service](../firmware/main/ir_service.cpp), [console handlers](../firmware/main/terminal.cpp), [line reader](../firmware/main/console_line.cpp), [Matter adapter](../firmware/main/matter_app.cpp), and [startup](../firmware/main/app_main.cpp). The [operation guide](operation.md) connects these paths to observable behavior.
6. **Review host integration and verification.** Inspect the [serial client](../tools/ir_terminal.py), its [tests](../tests/test_serial_client.py), and the [host-check script](../tools/test-host.sh). Use the existing checks for authorized changes while retaining their hardware limitations.
7. **Build with the selected SDKs.** Follow the [build guide](build.md) and [SDK reference](sdk-reference.md). Validate configuration before compilation, and preserve partition compatibility when changing storage or deployment settings.
8. **Qualify the physical workflow.** Complete the staged [bring-up procedure](bring-up.md) before treating flashing, capture/replay, profile activation, commissioning, or persistence as verified. Record conditions and measurements separately from host/build results.
9. **Prepare delivery when its scope is defined.** Follow [repository preparation](../CONTRIBUTING.md#repository-preparation), confirm hosted checks, and define any required release/provisioning process without treating local binaries as a published release.
