# Prioritized remaining-work checklist

This checklist converts the [programming index](programming-index.md#missing-partial-and-unclear-work) into proposed work and completion criteria. Priorities apply to qualifying the existing ESP32-S3 IR implementation. They do not establish new product requirements, change hardware roles, or authorize implementation of optional features.

**Status: 2026-10-28.** M1 and M2 are complete for the [defined local development scope](delivery-requirements.md), with [artifact-export evidence](validation.md#m1-and-m2-local-export-verification-2026-10-28). M3 is deferred and work is stopped. S1–S6 remain complete, with [host-test and target-build evidence](validation.md#s1-and-s2-verification-2026-10-28), [direct service/storage evidence](validation.md#s3-and-s4-verification-2026-10-28), and [Matter/startup regression evidence](validation.md#s5-and-s6-verification-2026-10-28). The other 22 items remain open, deferred, or conditional, including appliance setup, hosted verification, and physical qualification. An unchecked verification item does not imply a known code defect.

| Priority | Meaning |
|---|---|
| **P0 — prerequisite** | Resolve before the dependent activity, such as profile activation or powered hardware testing |
| **P1 — prototype qualification** | Establish that the existing implementation works under recorded conditions |
| **P2 — delivery readiness** | Complete when repeatable distribution or deployment is in scope |
| **P3 — conditional extension** | Unimplemented capability requiring an explicit requirement before development; reprioritize if it becomes necessary for a selected appliance or delivery goal |

Suggested order: identify appliances (**A1**) and complete the board prerequisite (**H1**). Existing checks/builds and direct service, Matter, and startup tests (**S1–S6**) passed for the recorded source. Hosted verification (**S7**) remains dependent on separately authorized publication. Continue bench work in **H2–H8** order. Appliance activation (**A6**) depends on confirmed captures, and controller acceptance (**H8**) follows activation. Conditional programming does not block testing the existing baseline.

## Physical hardware testing

Follow the existing [bring-up procedure](bring-up.md) for test methods and numerical limits. This checklist summarizes dependencies and acceptance evidence rather than replacing that procedure. H1 is a hardware-realization prerequisite, not a software task.

- [ ] **P0 · H1 — Complete the hardware package and obtain an assembled test board.** Capture the schematic, audit pins/footprints against the schedules and component references, complete PCB layout and ERC/DRC review, and resolve release-blocking findings before fabrication/assembly. Completion: an identifiable board revision, BOM, fabrication package, and assembly are available. The index records this prerequisite as unfinished. See [hardware package status](../hardware/README.md).
- [ ] **P0 · H2 — Qualify unpowered wiring and the power path before functional testing.** Inspect polarity, continuity, shorts, emitter harnesses, USB-C current-advertisement behavior, rails, startup/load transients, current limiting, discharge, and back-powering. Completion: measured results satisfy the [unpowered inspection](bring-up.md#1-unpowered-inspection) and [power qualification](bring-up.md#2-power-qualification) criteria; unresolved faults block later tests.
- [ ] **P1 · H3 — Verify reset, programming, console, and startup outputs.** After H2 and S2, exercise BOOT/reset, native USB and the intended recovery path, PSRAM initialization, console input, button, and indicator. Observe output inhibition during power-on, reset, download entry, and fault/recovery conditions. Completion: the flashed build is identified and no unintended emitter drive is observed. See [reset and programming](bring-up.md#3-reset-and-programming).
- [ ] **P1 · H4 — Qualify emitter drivers and protection.** After H3, measure each zone's current, carrier/duty, envelope timing, isolation from other zones, disable behavior, thermal performance, and bounded open/short responses using the documented test setup. Completion: electrical and thermal results meet the selected component/circuit limits for recorded cables and conditions. See [driver tests](bring-up.md#4-driver-electrical-tests).
- [ ] **P1 · H5 — Qualify reception and learned replay.** After H4, test all receiver paths with known sources, carrier-band edges, long frames, repeats, overflow/truncation cases, interference, and concurrent Wi-Fi/Matter activity. Compare optical replay with the original waveform. Completion: supported captures are complete and accurate under recorded conditions; unsupported/truncated cases are identified. See [receiver and learning tests](bring-up.md#5-receiver-and-learning-tests).
- [ ] **P1 · H6 — Verify physical persistence and interruption recovery.** After H5, test save/read-back, reboot/power removal, lost unsaved captures, interrupted writes/overwrites, brownouts, Matter reset, and compatible application updates on a test unit. See [storage interruption tests](bring-up.md#7-persistent-storage-and-interruption-tests).

See [appliance acceptance](bring-up.md#6-appliance-and-matter-validation).
- [ ] **P1 · H8 — Validate Matter operation and recovery end to end.** After A6, commission with the intended controller, exercise enabled light/fan controls, identify/button behavior, reboot, Wi-Fi loss/recovery, recommissioning, and missed IR. Successful Matter writes alone do not prove appliance response. See [Matter acceptance](bring-up.md#6-appliance-and-matter-validation) and [state limitations](appliance-profiles.md#matter-state-and-feedback).
- [ ] **P2, deployment-dependent · H9 — Complete qualification for the intended installation or product.** Determine the required enclosure, environmental, EMC/ESD, USB/RF, and product-level acceptance scope; perform the selected checks and document remaining limits. Completion: evidence applies to the final assembly and installation conditions. Module certifications or prototype bench checks alone do not establish final-product acceptance. See [hardware verification limits](../hardware/sources.md#verification-limits).
